# Implementation Plan

Start from a supplied plan, a requirements PDF without a plan, or a task in chat. Inspect the project, settle decisions through questions, then follow the user's selected implementation or package action. Packages follow the document ownership of BALE's HIRING_AND_WORKFORCE package. Read [the package contract](references/package-contract.md) before drafting or revising files.

## Chat commands

- `<source-file> [--project PATH] [--max-phases N] [--skills name1,name2] [--skills-mode auto|all] [--commits off|scoped]`: preferred start with an existing UTF-8 Markdown plan or PDF requirements/plan document. The path may also follow options such as `--skills`. Quote paths with spaces. A path-like argument that does not exist is an error, not a new task.
- `create "<task>" [same options]`: start without a plan file. `$implementation-plan "<task>"` remains an alias when the text is not path-like. Bare invocation asks for a plan path or task. Neither form writes files before the questions are answered.
- `revise <package-path> "<changes>" [same planning options]`: preserve the old revision and generate a new one. Read its current evidence and carry forward valid decisions, phase identity, status, and handoff. Inherit unspecified options. A different `--project` is invalid.
- `skills <package-path>`: list selected skills and their assignments. `--add name1,name2`, `--remove name1,name2`, and/or `--skills-mode auto|all` create a revision; adding and removing the same name is invalid. Leave other package options unchanged.
- `prompt <package-path> <phase-id>`: show the exact stored copyable prompt. This is read-only and does not execute it.
- `check <package-path>`: inspect structural and semantic consistency; do not edit. Report missing coverage, dependencies, stale references, unavailable skills and evidence limits.
- `status [package-path]`: with a path, show recorded phase states, actual evidence and next action; without one, list recognized packages in the current project. Do not infer implementation from a planning document.
- `help`: explain these commands without creating files.

Commands are agent-chat requests, not a shell CLI. Reject unknown options or conflicting values before acting. `--max-phases` must be a positive integer and is a hard upper bound, including integrated verification. Do not omit requirements or hide additional phases as subphases to fit a cap; ask for a changed cap or scope if needed. `--skills-mode auto`, `--commits off` are defaults. No `run`, `--auto`, or all-phase executor exists.

## Questions and action choice

1. Resolve the target project and applicable instructions. Read the supplied file without changing it, or gather the task when no file was supplied. For a PDF, use available PDF reading tools to inspect every relevant page, including tables or diagrams; if text or layout cannot be read reliably, ask for an accessible copy before drafting. Decide from the content whether the file is already a plan or is source requirements needing a plan. Trace current behavior, owners, public contracts, tests, Git roots and relevant existing plans. Distinguish implemented, missing, conflicting and unknown work. Check internal numbering and cross-references; ask about material contradictions, suggested-but-unconfirmed details, scope, product behavior, data, security, acceptance, selected skills or hard-to-reverse choices that source inspection cannot settle. Use the host's question interface when available and ordinary chat otherwise.
2. **Always ask the user to choose phase sizing before writing or implementing**, even when `--max-phases` was supplied. Offer **Compact** (a recommended exact count with fewer coherent phases), **Balanced** (a recommended exact count with more room for implementation and proof), and **Custom maximum** (the user supplies a positive hard cap). Include one phase when the work can reasonably finish in one session. For Custom maximum, derive an exact count within the cap and confirm it with the user before acting. A supplied `--max-phases N` pre-fills the custom maximum for confirmation; it does not skip the question. Show what work and proof fit each recommendation. If the cap cannot cover the work, explain why and ask for a higher cap or narrower scope.
3. **Always ask for the final action** after the plan and phase choice are clear: **Implement now**, **Prepare phase package**, or **Prepare package, then implement**. Recommend Implement now when the complete work, checks and handoff fit one session; otherwise recommend Prepare phase package. The user's answer, not the recommendation, selects the action. Missing required answers stop before writes or implementation.

Native Codex or Claude Plan mode may be used to prepare the plan and ask questions, but this skill also works without it. A repository skill cannot add an item to a host-owned Plan mode menu. If the host is still in a read-only planning mode, present the chosen action as a handoff and wait until execution mode permits writes; do not create a package or edit application code inside that mode.

## Prepare a package or revise one

1. Build a requirement-to-phase and acceptance map from the source file or chat task, answers and repository evidence. Assign dependencies before consumers and put integrated proof at the end. Preserve the supplied source as evidence while recording accepted clarifications in `PLAN.md`. If the source is only requirements, create the agreed working plan from those answers; do not treat the requirements as an already approved implementation plan. If revising, map old to new phases and carry actual proof forward only while it remains valid.
2. Inspect each named skill's installed `SKILL.md` and necessary references. Do not invoke it during planning. In `auto` mode put it in relevant phase prompts with a one-line reason in PHASES.md and `.package.json`; general style skills can appear everywhere, UI skills only where UI changes are in scope. In `all` mode include all selected skills in every prompt. Surface incompatible instructions or unavailable skills, and mark affected prompts pending rather than inventing behavior or installing a skill. Use host-appropriate `$name` (Codex) or `/name` (Claude Code) lines at the start of prompts.
3. Resolve the installed skill directory containing this `SKILL.md`. Use its bundled [package store](scripts/package_store.py) with Python 3.11+ to reserve a safe revision: `python <installed-skill-dir>/scripts/package_store.py start --project <project> --feature <feature> --phase-count <confirmed-count> [options]`. Pass `--max-phases <confirmed-cap>` only when a cap was set; the helper verifies the exact chosen count and the cap separately. For a Markdown plan, pass `--source-plan <exact-plan-file>`; the helper copies its bytes into `ORIGINAL_PLAN.md` and records a checksum. For a PDF, pass `--source-document <exact-pdf-file>`; the helper preserves the original bytes as `SOURCE_DOCUMENT.pdf` with a checksum. After reservation, write the agreed plan into `ORIGINAL_PLAN.md` for PDF or chat-only input. Never replace the original PDF with extracted text. For a revision pass `--previous <exact-package-path>` and inherited options; it carries forward existing source snapshots unless a new source is explicit. For an older package without one, write a session baseline derived from its `PLAN.md` and label that origin honestly. The helper returns the exact output path. Do not copy BALE's domain content or paths.
4. Write all 11 shared documents and separate phase prompts according to the package contract. Then update that revision's `.package.json` `phases` map (`P01` to prompt filename) and `skill_assignments` map (skill name to phase IDs and reason), keeping other metadata intact. Leave status `draft` until manual semantic review and helper checks pass; then set `ready`. Use only the selected revision path. Preserve earlier revisions and unrelated work.
5. Run `python <installed-skill-dir>/scripts/package_store.py check --package <exact-package-path>` and review links, feature/acceptance coverage, phase dependencies, prompt scopes, skill routing, commit language, status, UTF-8 and final newlines. For pathless `status`, use the helper's `list --project <project>` command; its `status`, `skills`, and `prompt` commands accept `--package`. The helper's structural pass does not prove content quality or agent adherence. Report the path, phase count, selected skill placements, Git exclusion result and remaining prerequisites.

## Execution boundary

Implement now edits the application only after the user selects it and the host permits writes. If the plan has multiple phases, implement only the first ready, selected phase and stop; do not continue automatically. Use relevant selected installed skills during that implementation; `all` mode applies every selected compatible skill to that scope. Prepare phase package writes only planning files. Prepare package, then implement first completes and checks the package, then invokes only its first ready prompt in the same authorized request. An unavailable required skill or unresolved blocker stops dependent implementation.

Each generated prompt covers exactly one phase and stops there. With `--commits off`, it may prepare messages but must not authorize a commit. With `--commits scoped`, its invocation authorizes only owned local commits after implementation and required checks pass, subject to repository instructions and later user limits. Direct implementation follows the same commit policy. No prompt authorizes a push, deployment, production data change or another phase. Read-only or package maintenance commands do not implement a phase.

## Generated artifacts

Place new packages under `<project-root>/.implementation-plans/<descriptive-feature>-implementation/`, with each revision in an exclusively created `YYYYMMDDTHHMMSSZ-<unique-id>/` directory. The output root and feature folder have ownership markers; each revision has `.package.json`. Preserve previous revisions and resume an identified unfinished revision instead of creating an empty replacement. Existing `docs/<feature>/<run-id>` packages remain readable and revisable; save their new revisions under `.implementation-plans/` without moving the old files. Reject linked paths, traversal, tracked output and unrelated same-name folders.

Before writing package content, resolve the repository root and inspect `.gitignore`. Add the root-anchored `/.implementation-plans/` rule only when needed. Refuse an existing unowned output root; leave `docs/` and any prior ignore rules untouched. Preserve existing bytes and line endings, verify effective exclusion with `git check-ignore`, and never untrack files automatically. The helper performs these operations; do not bypass a failure. Outside Git, use the selected project directory and disclose that Git exclusion is unverified. Skill installation files are never a package destination.
