# Implementation Plan

Start from a supplied plan, a requirements PDF without a plan, or a task in chat. Inspect the project, settle material decisions, then present a plan in chat or prepare a safely stored package. **This skill only plans: never edit application code, run an implementation or merge prompt, create branches or worktrees, merge, delete branches, or make a commit.** Default planning is detailed and sequential on the current branch; never switch to main automatically. Read [the package contract](references/package-contract.md) for detailed packages, or [light planning](references/light-planning.md) only when `--light` is selected.

## Chat commands

- `<source-file> [--project PATH] [--max-phases N] [--skills name1,name2] [--skills-mode auto|all] [--commits off|scoped] [--auto-commit] [--test-scope focused|full] [--light]`: preferred start with an existing UTF-8 Markdown plan or PDF requirements/plan document. The path may also follow options such as `--skills`. Quote paths with spaces. A path-like argument that does not exist is an error, not a new task.
- `create "<task>" [same options]`: start without a plan file. `$implementation-plan "<task>"` remains an alias when the text is not path-like. Bare invocation asks for a plan path or task. Neither form writes files before the questions are answered.
- `revise <package-path> "<changes>" [same planning options]`: preserve the old revision and generate a new one. Read its current evidence and carry forward valid decisions, phase identity, status, and handoff. Inherit unspecified options. A different `--project` is invalid.
- `skills <package-path>`: list selected skills and their assignments. `--add name1,name2`, `--remove name1,name2`, and/or `--skills-mode auto|all` create a revision; adding and removing the same name is invalid. Leave other package options unchanged.
- `prompt <package-path> <prompt-id>`: show the exact stored copyable Pxx execution prompt. Light P01 comes from `PLAN.md`. This is read-only and does not execute it.
- `check <package-path>`: inspect structural and semantic consistency; do not edit. Report missing coverage, dependencies, stale references, unavailable skills and evidence limits.
- `status [package-path]`: with a path, show recorded phase states, actual evidence and next action; without one, list recognized packages in the current project. Do not infer implementation from a planning document.
- `help`: explain these commands, optional user settings, planning-only boundary and later phase-specific invocation without creating files.

Commands are agent-chat requests, not a shell CLI. Reject unknown options or conflicting values before acting. `--auto-commit` conflicts with any `--commits` value; record it as `--commits auto` in the package store for later phase prompts only. `--max-phases` must be a positive integer and is a hard upper bound, including integrated verification. Do not omit requirements or hide additional phases as subphases to fit a cap; ask for a changed cap or scope if needed. Without a user config, `--skills-mode auto`, `--commits off`, and `--test-scope focused` are defaults. A plain-language request for the full backend or other named suite selects full scope for that suite in the future phase prompts; it does not run tests during planning. No `run`, `--auto`, or all-phase executor exists.

`--light` selects one coherent task with compact documentation. A supplied maximum remains a cap, not a requested count. New work defaults to detailed; revisions inherit their profile unless explicitly changed. A natural request to expand a light package creates a detailed revision without discarding retained requirements or evidence. Disclose the resolved profile alongside the brief settings line. Preserve existing user-config keys.

## User settings

For new work, read `~/.config/implementation-plan/config.json` (on Windows, under the user's profile). It is optional; [the bundled template](assets/config.json) shows the exact schema. Require `schema_version: 1` and complete `defaults_at_setup` and `current` objects with `commits: off|scoped|auto`, `test_scope: focused|full`, and `skills_mode: auto|all`; reject unknown or invalid fields before writes. Only `current` controls settings for new plans and their future phase prompts. `defaults_at_setup` is a historical reference and stays unchanged when the user edits `current`. Explicit chat options override `current` for that request. Before planning new work, state the resolved settings in one short line, marking values changed from setup defaults; for example, `Commits auto (was off) | Tests focused | Skills auto`. A configured auto-commit setting applies only to later, separately invoked implementation prompts, never to this skill's planning or package preparation.

For an existing package, use its saved `.package.json` settings rather than rereading the user config; display that package's resolved settings before a revision. Config edits affect only new work. `revise <package-path> "<changes>" --commits off` or another explicit planning option changes an existing package in a new revision. A later user instruction or repository rule that limits commits takes precedence. Missing config means the built-in defaults above. If config is malformed or unreadable, report its path and stop before making changes; do not silently fall back.

## Questions and action choice

1. Resolve the target project and applicable instructions. Read the supplied file without changing it, or gather the task when no file was supplied. For a PDF, use available PDF reading tools to inspect every relevant page, including tables or diagrams; if text or layout cannot be read reliably, ask for an accessible copy before drafting. Decide from the content whether the file is already a plan or is source requirements needing a plan. If request-review or plan-review findings are supplied, carry their request IDs, decisions, gaps and limits forward as review evidence; verify against current source and do not treat a client summary alone as a complete handoff or approval to implement. Trace current behavior, owners, public contracts, tests, Git roots and relevant existing plans. Distinguish implemented, missing, conflicting and unknown work. Check internal numbering and cross-references; ask about material contradictions, suggested-but-unconfirmed details, scope, product behavior, data, security, acceptance, selected skills or hard-to-reverse choices that source inspection cannot settle. Use the host's question interface when available and ordinary chat otherwise.
2. For detailed planning, **ask the user to choose phase sizing before presenting a new plan or writing a package**, even when `--max-phases` was supplied. Offer **Compact** (a recommended exact count with fewer coherent phases), **Balanced** (a recommended exact count with more room for implementation and proof), and **Custom maximum** (a positive hard cap). Include one phase when work and proof fit one session. Derive and confirm an exact count within a custom cap. Count integrated verification explicitly; do not hide it to fit a cap. With `--light`, skip this question and use exactly one coherent task. If light scope is too broad, explain the mismatch and settle reduced scope or detailed mode before writes.
3. Resolve the final action: **Present plan in chat** or **Prepare package**. Honor an explicit selection already made; otherwise ask, recommending a package. Missing required answers stop before package writes. Neither action authorizes application implementation or Git execution.

Native Codex or Claude Plan mode may be used to prepare the plan and ask questions, but this skill also works without it. A repository skill cannot change a host-owned **Implement plan** menu item. In read-only Plan mode, do not write package files. If the user selected a package, make the host plan's executable steps exclusively about creating and checking that package after writes become available; describe the application phases as package content, not work to execute. State that the host's **Implement plan** action authorizes package creation only and stops after its check. If the user selected chat only, present the detailed plan without application edits; a later generic **Implement plan** action does not identify a package and phase. After a package is prepared, treat “go ahead” or “implement the plan” as ambiguous and ask for the exact package path and phase ID. A later application implementation requires a separate request such as `Implement P01 from <package-path>` or direct invocation of that package's stored phase prompt, outside this planning skill.

For either output, make the plan specific enough for another session to execute safely: map every requirement to a phase and observable acceptance criterion; identify current source evidence and uncertainties, owners, dependencies, contracts, data and permission effects, failure paths, verification commands or missing prerequisites, and stopping conditions. **These feature-specific details are mandatory in every normal plan and new package, regardless of model, effort setting or terse chat style. Only explicit light mode reduces document structure.** Do not substitute length, copied headings or invented details for evidence. Instructions cannot guarantee equal reasoning quality across models; record unknowns and missing prerequisites honestly. In chat-only output, present the applicable details directly and mark implementation and application tests as not run.

## Prepare a package or revise one

1. Build a requirement-to-phase and acceptance map from the source file or chat task, answers and repository evidence. Assign dependencies before consumers and put integrated proof at the end. Preserve the supplied source as evidence while recording accepted clarifications in `PLAN.md`. If the source is only requirements, create the agreed working plan from those answers; do not treat the requirements as an already approved implementation plan. If revising, map old to new phases and carry actual proof forward only while it remains valid.
2. Inspect each named skill's installed `SKILL.md` and necessary references. Do not invoke it during planning. In `auto` mode put it in relevant phase prompts with a one-line reason in PHASES.md and `.package.json`; general style skills can appear everywhere, UI skills only where UI changes are in scope. In `all` mode include all selected skills in every prompt. Surface incompatible instructions or unavailable skills, and mark affected prompts pending rather than inventing behavior or installing a skill. Use host-appropriate `$name` (Codex) or `/name` (Claude Code) lines at the start of prompts. Do not put `$implementation-plan` or `/implementation-plan` in an execution prompt.
3. Resolve the installed skill directory containing this `SKILL.md`. Use its bundled [package store](scripts/package_store.py) with Python 3.11+ to reserve a safe revision: `python <installed-skill-dir>/scripts/package_store.py start --project <project> --feature <feature> --phase-count <confirmed-count> [options]`. For light pass internal `--profile light --phase-count 1`. Pass `--max-phases <confirmed-cap>` only when a cap was set; the helper verifies the exact chosen count and cap separately. Pass `--commits auto` when `--auto-commit` was explicitly selected. Omitted commit, test-scope and skills-mode options use `current` from the user config for new packages or built-in defaults; revisions inherit saved policies, skills, profile and sizing unless overridden. For Markdown pass `--source-plan <exact-file>` to preserve its bytes in `ORIGINAL_PLAN.md`; for PDF pass `--source-document <exact-file>` to preserve `SOURCE_DOCUMENT.pdf`. Both snapshots are checksummed. Write the agreed working plan into `ORIGINAL_PLAN.md` for PDF or chat input. Never replace the PDF with extracted text. For a revision pass `--previous <exact-package-path>`; use `--profile detailed` for an explicit expansion from light and pass the newly confirmed count. Preserve source snapshots. For older packages without one, derive a session baseline from `PLAN.md` and label the origin. Use the helper's returned path; do not copy another project's domain content.
4. For detailed packages write all 11 shared documents and separate prompts according to the package contract. For light use its reference's single `PLAN.md` contract. State test scope, commit policy and the commit-only follow-up rule in every execution prompt. Detailed commit drafts with substantive bodies remain required, in `COMMIT_MESSAGES.md` or the light plan's commit-draft section; refresh them against actual diffs and checks later. Update `.package.json` `phases`, `skill_assignments` and `dependencies`. Put the exact revision path and commit-draft pointer in the handoff. Leave status `draft` until manual semantic review and helper checks pass; then set `ready`. Preserve earlier revisions and unrelated work.
5. Run `python <installed-skill-dir>/scripts/package_store.py check --package <exact-package-path>` and review links, feature/acceptance coverage, phase dependencies, prompt scopes, skill routing, detailed commit bodies, status, UTF-8 and final newlines. For pathless `status`, use the helper's `list --project <project>` command; its `status`, `skills`, and `prompt` commands accept `--package`. The helper's structural pass does not prove content quality or agent adherence. Report the path, phase count, selected skill placements, Git exclusion result and remaining prerequisites.

## Execution boundary

This skill may write only package planning files and the narrowly required root `.gitignore` rule. It never invokes a phase prompt, edits application code, runs application tests, commits, or automatically continues from planning into implementation. A generated phase prompt is an instruction for a later, separately requested session with an exact package path and phase ID. An unavailable required skill or unresolved blocker leaves the dependent phase prompt pending.

Each generated prompt covers exactly one phase and stops there. With effective commit policy `off`, it may prepare messages but must not authorize a commit. With effective policy `scoped`, its later invocation permits only owned local commits after implementation and required checks pass, subject to repository instructions and later user limits. With effective policy `auto` from the user config or `--auto-commit`, a later invoked phase prompt must commit only its verified, owned changes locally after required checks pass, without another commit question. Require that prompt to inspect the Git root, status and diff; stage explicit owned paths; use a Conventional Commit subject, blank line and substantive body grounded in the actual changes, reason and completed checks; verify the committed message, changed paths and remaining status. A subject-only commit does not satisfy this policy. If checks fail, required prerequisites are missing, or there are no owned changes, the prompt must forbid a commit and report why. Package preparation and revision never commit. No prompt authorizes a push, deployment, production data change or another phase.

For generated phase prompts, treat detailed commit messages as a required handoff regardless of commit policy. Separate repositories and unrelated features. Instruct the later implementing agent to ground each final message in the actual diff, explain behavior and reason in the body, and include only checks that ran; record an unfinished message as a draft rather than compressing it to a subject. Do not let a selected terse speaking style shorten commit text. In light packages, all references below to `COMMIT_MESSAGES.md`, `PROGRESS.md` and `HANDOFF.md` mean their named sections in `PLAN.md`; do not create duplicate files just to satisfy a pointer.

Every generated phase prompt and `HANDOFF.md` must also cover a later explicit commit-only request such as "commit it". If the active package revision is identified by that prompt or handoff, read its `COMMIT_MESSAGES.md` on every such request, even when the saved commit policy is `off`. Match drafts to the affected repository and logical feature; inspect current Git roots, status, staged and unstaged owned changes, and recorded checks before adapting the subject and detailed body to what actually changed. The draft is a starting point, not authority to include unrelated files or claim unrun checks. Stage only owned paths, commit only the requested completed work, and verify the message, changed paths and remaining status. An explicit later request authorizes that commit only; it does not turn on automatic commits, push, deployment or another phase. Do not rerun tests, edit application code or revise the package solely for a commit-only request unless a repository rule or hook requires it. If the active package is ambiguous, ask for its exact path instead of guessing the newest revision; if its commit-message file is missing or unreadable, disclose that and use a message grounded in the actual diff only if the commit is otherwise authorized.

Record the later implementation test policy in the relevant prompts: `focused` runs tests and checks covering changed behavior and affected integrations; `full` also runs the complete configured test suite for each component changed in the selected phase, or the explicitly named suite such as the backend suite. Repository-required gates still apply in either mode. Find actual project commands when available; do not invent a generic test command. Require the later agent to report skipped, interrupted and failing suites accurately, separating failures caused by the change from unrelated failures. Package creation does not execute application tests or claim they passed.

## Generated artifacts

Place new packages under `<project-root>/.implementation-plans/YYYYMMDDTHHMMSSZ-<descriptive-feature>/`, with each revision in an exclusively created `YYYYMMDDTHHMMSSZ-<unique-id>/` directory. The UTC timestamp on the feature folder makes new folders sort by creation time; revisions keep their original feature folder. The output root and feature folder have ownership markers; each revision has `.package.json`. Preserve previous revisions and resume an identified unfinished revision instead of creating an empty replacement. Existing feature folders and `docs/<feature>/<run-id>` packages remain readable and revisable without renaming or moving them. Reject linked paths, traversal, tracked output and unrelated same-name folders.

Before writing package content, resolve the repository root and inspect `.gitignore`. Add the root-anchored `/.implementation-plans/` rule only when needed. Refuse an existing unowned output root; leave `docs/` and any prior ignore rules untouched. Preserve existing bytes and line endings, verify effective exclusion with `git check-ignore`, and never untrack files automatically. The helper performs these operations; do not bypass a failure. Outside Git, use the selected project directory and disclose that Git exclusion is unverified. Skill installation files are never a package destination.
