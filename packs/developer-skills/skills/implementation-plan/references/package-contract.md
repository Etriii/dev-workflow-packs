# Implementation package contract

The package records a detailed plan, not completed work. Make every file specific to the feature and current repository. Scale detail to complexity while preserving these document owners. Do not fill documents with copied headings or invented test results. Package creation and checking end this skill's work; application changes require a later request naming the exact package and phase.

| File | Owns |
|---|---|
| `ORIGINAL_PLAN.md` | Unchanged snapshot of a supplied Markdown plan, or the agreed working plan when the input was a PDF or chat task. Record later clarifications in `PLAN.md`. |
| `SOURCE_DOCUMENT.pdf` | Exact, checksummed copy of a supplied PDF, when present. It remains the original evidence even if the working plan is revised. |
| `README.md` | Purpose, how to use one phase prompt, file ownership and repository boundaries. |
| `PLAN.md` | Goal, approved decisions, exclusions, current source evidence and requirement-to-phase coverage. |
| `CONTRACTS.md` | Shared business, API, data, permission and failure invariants that phases must preserve. |
| `PHASES.md` | Ordered tasks, dependencies, deliverables, acceptance ownership and selected-skill assignments with reasons. |
| `PROMPTS.md` | Index linking each executable `prompts/Pxx_*.md`; no duplicated prompt bodies. |
| `RUNBOOK.md` | Shared preflight, selected test scope and actual suite commands, Git, recovery and stop rules. |
| `ACCEPTANCE.md` | Stable observable criteria, including failure and forbidden paths where relevant. |
| `PROGRESS.md` | Sole status, evidence, decision, blocker and commit-outcome ledger. Begin with no implementation proof unless current source provides it. |
| `HANDOFF.md` | Immediate next action, unresolved issues and recovery point; link to PROGRESS.md for history. |
| `BLOCKERS.md` | Actual blocking decisions and dependency impact, with prospective cases clearly labeled as examples. |
| `COMMIT_MESSAGES.md` | Detailed, copyable draft messages by repository and logical feature; no fabricated validation or commit hashes. |

The phase list must match the user's confirmed exact count; an optional maximum remains a separate cap. For each phase, identify the requirement and acceptance IDs it owns, current source evidence, exact objective, responsible components, dependencies, planned behavior and contracts, data or permission effects, failure paths, deliverables, relevant verification commands or missing prerequisites, and the stop and handoff condition. Put shared invariants in `CONTRACTS.md` and link them rather than repeating them. A plausible heading without feature-specific decisions is incomplete.

Each phase prompt names only its phase, project path and package path, prerequisites, relevant source and package sections, deliverables, acceptance checks, selected test scope, commit policy, tracking updates and stop condition. It is a later execution instruction, never a task to start while preparing this package. Do not put the planning skill invocation in an execution prompt. Keep the prompt self-contained enough to start in a fresh session while linking shared detail rather than duplicating whole specifications. With commit policy `auto`, instruct the later implementing agent to commit its verified, owned local changes after required checks pass using the updated detailed message, verify the committed message and changed paths, then record the commit and remaining Git status in `PROGRESS.md`; failed checks, missing prerequisites and no owned changes prevent a commit. Preparing or revising the package does not commit. Use descriptive user-facing objectives; retain phase IDs only where technically needed. In `full` scope, require the complete configured suite for each changed component or the explicitly named suite, such as the backend suite. Package creation does not run application tests. Unknown commands remain prerequisites, not fabricated commands or passing evidence.

Commit messages are a required package deliverable even with `--commits off`. For each expected repository and distinct logical change, provide a separate labeled, copyable fenced message with a Conventional Commit subject, a blank line, and a substantive body. Explain the intended behavior and why it matters, then give concrete planned components or changes, relevant migration/configuration/compatibility effects, and the verification expected for that group where applicable. Mark unimplemented details and unrun checks as planned or `NOT_RUN`; do not invent file paths, test results or commit hashes. During implementation, revise each draft against the actual diff and completed checks before presenting or using it. Use the existing message for a coherent change even if it spans several files; never combine unrelated repositories or features to save space. If verification makes no changes, state that no commit is expected rather than inventing a test-only commit. Subject-only lists, terse placeholder bodies and phase labels in Git subjects fail package review. This level of detail is required regardless of caveman or other terse response styles; those styles apply to chat, not persisted commit messages.

Record the source evidence used during planning and its limits. Keep a supplied Markdown plan's original bytes in `ORIGINAL_PLAN.md` and put later answers in `PLAN.md`. For PDF input, keep the original PDF in `SOURCE_DOCUMENT.pdf` and write the agreed working plan in `ORIGINAL_PLAN.md`; do not present the latter as a byte-for-byte PDF copy. The store checks supplied-file snapshot hashes. A plan created from chat is recorded before deriving the package documents. Unrun tests are `NOT_RUN`; later requirements are `DUE_LATER` only with their owner phase. Completion requires actual implementation and required proof, not a checked box, generated prompt, or prepared commit message. A revision links to its predecessor, retains valid results and marks invalidated evidence for recheck.

If a selected skill is unavailable, list its exact name, affected prompts and installation prerequisite. The output still may be saved as a draft; do not label affected prompts ready. In `all` mode, every prompt includes all selected skills, but their instructions remain limited by selected-phase scope and repository policy. Detect scope or workflow conflicts before saying a prompt is ready.

The helper verifies safe storage, basic files and the presence of copyable commit subjects with bodies. The author must also check whether those bodies are specific and complete, local Markdown links, coverage of every requirement, one owner for each acceptance case, dependency order, appropriate skill assignment, and no hidden commit authorization. Do not label an unchecked item passed.
