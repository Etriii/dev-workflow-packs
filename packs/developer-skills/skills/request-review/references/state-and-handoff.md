# Decision state and planning handoff

Chat-only work may keep this structure in conversation. On save or fresh-session handoff, write a readable `reviewed-requirements.md` and `review-state.json` inside the same run. The JSON is a small ledger, not an interpretation engine; [review_state.py](../scripts/review_state.py) validates it. Do not persist unnecessary personal data, credentials or raw logs. Preserve original source wording; a PDF reference alone is insufficient for a request extracted from it.

`--client` and its detailed form read the identified review without applying new defaults or changing decision provenance. Their page-only display does not remove source filenames from the ledger or full handoff. An explicit “save this client summary” adds `client-summary.md` beside the full handoff under the same storage/revision rules; a client summary cannot replace the requirements used for planning. Client presentation maps the existing decision records to short proposed markers and plain answers; no schema migration or separate approval store is needed.

## JSON ledger, schema version 1

Top-level keys: `schema_version` (1), `repositories`, `sources`, `requests`, `decisions`. Optional `revision_of` points to the preceding saved review path. `repositories` is a list of objects with stable `name`, `path`, and `availability` (`available` or `unavailable`). The path is for re-opening the repository; prose reports use relative file paths. `sources` holds `id`, `kind` (`chat`, `pdf`, `markdown`, `text`), `reference`, and `items`. Each item has unique `id`, `original` text and optional positive physical `page` and `printed_label`. For PDF sources, `pages` lists physical page numbers with `status` (`readable`, `partial`, `unreadable`) and the methods actually used (`text`, `render`, `visual`, `ocr`, `annotations`). Missing content is described in `unreadable`. A source item may map to several requests and a request may map to several source items.

Each `requests` object has unique stable `id` (`REQ-01` and so on), `source_ids` (nonempty existing source-item IDs), `english`, `category`, `type`, `assessment`, `readiness`, `scope` (`included`, `excluded`, `superseded`), `locations`, `evidence`, `files`, `acceptance`, `dependencies`, `unresolved_facts`. A location has `kind` (`page`, `job`, `service`, `integration`, `configuration`), `name`, `repository`, and for a page, `route`/`access` values or explicit `Route not yet verified`/`Access not yet verified`; `conditions` records important restrictions. Evidence entries have `level` (`reported`, `source`, `test`, `runtime`, `deployed`, `history`), `finding`, and optional repository/relative file/lines. File entries have `repository`, relative `path`, `existing` boolean, `action`, `purpose`, and optional inspected `lines`. A proposed file uses `existing: false` and action `Proposed addition`. Dependencies use request IDs. Acceptance checks are short observable statements tied to the current decision. `unresolved_facts` never acquire defaults.

Each decision has unique `id`, `request_ids`, `question`, `options` (objects with `id`, `label`, `effect`), `recommended` option ID or `null`, `rationale`, `selected` option ID or custom answer or `null`, `origin` (`pending`, `default applied`, `selected by user`, `existing verified requirement`), `unresolved_facts`, and optional `revisions` recording prior values/reasons. A default is eligible only if the option was presented and the missing information is a proposed choice, not a fact or authorization. An explicit answer overrides a default; update request English where decision-dependent, scope, recommendation, acceptance and summary before saving a new revision. The validator checks referential and provenance consistency; human review checks semantic consistency.

Use this same `decisions` list for user questions about choices, missing sources and factual verification, including questions asked through the host interface. New question IDs use `Q-01`; existing IDs remain valid and must not be renumbered. For an open factual question, use `options: []`, `recommended: null`, `selected: null`, `origin: "pending"` and record the missing evidence in `unresolved_facts` on the decision and affected requests. An explicit factual answer can be recorded as custom `selected` text with `origin: "selected by user"`; retain any verification limits until evidence resolves them. Keep answered entries and revisions. Link review-wide questions to the affected requests once identified; unresolved intake stays in conversation until a valid review can be recorded. This uses schema version 1 without adding another question store.

## Saved Markdown handoff

Label the file **Reviewed requirements**, never approved implementation plan. Include source inventory with original PDF basename and physical page references, repository mapping and availability, included/excluded/superseded ID list, each ID's original source mapping and English request, route/access or job/service location, finding with evidence level and limits, recommendation separated from request, relative source/test/config locations, explicit decisions and applied defaults with rationale and revisions, acceptance checks, dependencies and unresolved blockers. Carry partial PDF readability forward. A short confirmation summary can be included but cannot replace these sections. Preserve a source PDF in the run without altering its bytes; reference the copy. If an explicit project document path is used, place an appropriate source copy beside it only when safe and useful, and identify its location.

Preserve request order and question references beside affected requests. End the Markdown with the complete **Questions and answers** section specified in the output rules, including pending factual questions, all presented options and current answers, after verification and notes. Reconcile it with the conversation and ledger before saving; the helper's content checks do not prove final placement or completeness against unrecorded chat questions.

For multiple repositories, include each member's actual path in the private handoff for reopening in a fresh session; use repository names above file tables and paths relative to those roots. Missing members remain visible with partial coverage. Do not assume neighboring repositories belong to the same application. A compatible existing `change-report`/`bug-investigation` project registry may be read or updated by its own owner when requested; this skill has no competing registry. Natural external paths and confirmed membership can be recorded in the review state.

When invoking the installed `implementation-plan`, inspect its current `SKILL.md`; its source-file form accepts the Markdown handoff path. It independently asks phase sizing and final action. Its package store copies the supplied Markdown into `ORIGINAL_PLAN.md`; this is source evidence, not approval to implement. Do not transfer request-review defaults to implementation-plan's phase/action choices. If the user only asks to prepare a plan, obey that boundary. If unavailable, save the complete handoff and give the copyable path-based invocation for later use.

For a revised saved review, preserve the prior run. Resume its identified folder for ordinary unfinished work; when decisions materially change, save a new revision folder with `revision_of` pointing to the previous folder and copy forward valid evidence, source mappings and IDs. Check whether evidence has become stale before repeating it as current. Existing project documents requested explicitly follow their own ownership and version convention.
