# Review and output rules

## Evidence discipline

Read the current application before classifying each request. For access, follow actual middleware, policy, guard, signed-link verification and tenancy filters. A public route may still require a valid signed ticket. Record browser routes separately from API endpoints. If unverified, say “Route not yet verified” or name the access uncertainty; never fill a convenient route. For non-page work, name the job, service, integration or configuration instead. For each source file, verify existence and repository root. Use relative paths, and exact narrow line ranges only after inspecting those lines. Mark a suggested new path as **Proposed** and give it `—` for lines.

Keep three axes in state: request type (`Bug report`, `New feature`, `Improvement`, `Refactor`, `Removal`, `Needs clarification`); assessment (`Confirmed defect`, `Suspected defect`, `Existing behavior`, `Already satisfied`, `Partially implemented`, `Not reproduced`, `Unable to verify`, `Proposed change`); readiness (`Ready to plan`, `Needs clarification`, `Needs investigation`, `Already satisfied`, `Deferred or excluded by the user`). “Not reproduced” is inconclusive. A regression requires evidence of prior working behavior and later failure. A matching symptom does not prove cause. A local test or prior commit does not prove deployed behavior. Correct changed interpretations explicitly, with the new evidence. Do not claim performance, security or reliability benefits without evidence.

PDF pages are physical pages starting at 1. Record printed labels separately when they differ. Inventory all pages before declaring coverage. Text extraction alone cannot establish coverage of images, tables, annotations or diagrams. Render and inspect relevant pages; use OCR when needed and available, identify OCR uncertainty. If a page is unreadable, identify the page and dependent request; review readable material and leave the factual blocker open. Do not claim an inspection method that was not used. Preserve the source PDF byte-for-byte in a saved handoff when appropriate.

## Decisions

Questions belong in default and detailed reviews. Inspect first; ask one decision at a time or up to three closely related questions. Give up to three meaningful distinct options; best-supported first, **Recommended** and **Default**, with a short behavior/tradeoff and a custom answer path. Explain why the recommendation fits inspected behavior. The host may show a preselected answer, but it has not submitted it. Leave time for the user to answer; apply an unanswered eligible default only at the end of the review, on explicit skip or summary request. Record `Default applied` versus `Selected by user`. Factual blockers have no default. A later user answer replaces the applied default and invalidates stale wording and checks. “Use your recommendations” applies only recommendations already presented and eligible for defaulting.

Reuse the existing decision record for all questions; do not create a separate input queue. Give new questions stable `Q-01` IDs and retain existing decision IDs when resuming. Record questions asked through the host interface as well as in chat. Missing templates, business facts and verification that requires the user must become explicit, answerable questions, with affected request IDs and the consequence of waiting. Do not ask the user to do investigation the agent can perform. A factual question may have no meaningful options or recommendation; request the exact information or evidence needed instead of inventing choices. Never apply a default before the question and recommendation have been presented with a reasonable answer opportunity.

## Presentation

Use actual application areas, such as Announcements or Profile, or group by role when clearer. Avoid architectural grouping and repeating a shared request under each role. Plain concise English; no stock intro/recap, hashes by default, absolute machine paths, Project column, empty sections or repeated N/A. Original quotations retain their source language. Hyphens are list markers and separators. File operations (`Inspect`, `Proposed modification`, `Proposed addition`, `Proposed rename`, `Proposed removal`) differ from purpose (`New`, `Improvement`, `Fix`, `Refactor`, `Removal`, `Unclear`). Never label proposed work as completed.

Keep requests in their original source order with stable IDs. Do not move a request because it needs a question or verification; if grouping would reorder requests, repeat an area heading where necessary. Leave the finding and recommendation in place and add a short reference such as `Needs clarification — Q-02`, `Needs your verification — Q-03` or `Source needed — Q-04` in the recommendation/readiness cell. Resolved references show their current provenance. The full question and options belong in the final Q&A section.

Default review: begin each category with a Markdown table using these columns in this order:

`ID — Request summary | Original request — verbatim | Finding | Recommendation / readiness`

- **ID — Request summary:** stable `REQ-xx` ID and a concise English summary of the requested behavior, separate from the proposed solution. Keep source citations in the original-request cell and application routes in the page/access details, rather than varying the contents of request headings.
- **Original request — verbatim:** quote the relevant source passage, immediately followed by its source citation in the same cell: `“Exact source wording.” — requirements.pdf, page 6`. Use this placement for every PDF-derived request in default, detailed and saved reviews. Use physical page numbers starting at 1; include a differing printed page label separately. Repeat the quote-and-citation pair for each merged source passage, retaining every source/page mapping. For chat use `“Exact source wording.” — chat feedback`; for Markdown/text use the filename and an inspected section or line reference when available. If a PDF page is unverified, say `Source page not verified` rather than omitting or inventing it. Keep original language and wording, even when already English. Label excerpts and mark omissions without dropping material conditions or exceptions. Escape table delimiters and represent line breaks without changing the words. Never reconstruct a missing or unreadable passage; identify the source gap explicitly.
- **Finding:** explain current behavior, the gap or match against the request, and evidence level and limits. Connect the behavior to its practical consequence instead of giving only a status such as “Partially implemented.” If already satisfied, briefly state what satisfies it and what was verified; do not invent a gap or pad the row.
- **Recommendation / readiness:** explain the proposed behavior and material safeguards, dependencies or decisions still needed; state readiness when useful. Distinguish a proposal, an unanswered recommendation, `Default applied`, and `Selected by user`. For satisfied requests, recommend reuse when appropriate. Keep explanation depth proportional to the request while covering the same questions in every row.

Below the category table, add supporting details keyed by ID: **Page** with verified route/navigation, **Access** with material conditions, **Type**, a compact `File | Proposed action | Purpose` table, and any additional **Decision** reference. Omit inapplicable fields and avoid repeating the overview prose or full questions. Put a repository heading above a source table when multiple roots contribute. Include tests, config, migrations and integration locations when relevant.

Detailed keeps the same overview columns, categories, IDs and original quotations. Expand supporting details with current behavior and evidence, recommendation rationale, `File | Lines | Proposed action | Type | Purpose` table, data/access implications, acceptance checks, dependencies and remaining investigation where applicable. Do not repeat the overview paragraph under several headings. Use narrow inspected ranges or `—` for unavailable/proposed locations.

Summary reuses recorded state. State intended behavior by familiar category and page/route/access, keeping restrictions and dependencies that affect scope. Retain each request ID and its source citation; when the original quotation is omitted, place the citation immediately after the request description, including the physical PDF page. Briefly list applied defaults and unresolved factual blockers. Omit file tables, inspected code lines, logs and investigation history; retain presented options in the final Q&A but omit other rejected alternatives. Natural filters retain IDs and excluded history in state. If excluding one request breaks an included dependency, explain that consequence rather than silently dropping the dependency. State when summary evidence is from a prior review and may be stale; do not silently reassess code.

## Final questions and answers

End every default, detailed, summary and saved review with **Questions and answers**, after verification, notes and other closing material. List all questions raised during the identified review together, including those asked earlier through interactive prompts and those already answered or defaulted. The interactive three-question limit does not limit this final list. Order questions by their affected requests' original order, then by question order; keep IDs stable. Filtered views still retain the complete Q&A, marking questions about excluded or out-of-view requests accordingly without restoring their scope. If no questions were raised and none are needed, say so briefly here.

Each entry contains its question ID, affected `REQ-xx` IDs (or review-wide context for intake questions), the exact question, available options and tradeoffs, the **Recommended / Default** choice and rationale when applicable, and the current **Answer** with provenance: **Selected by user**, **Default applied**, **Pending**, or **Existing verified requirement**. For a pending factual question, say what evidence is needed and what remains unverified; there is no factual default. Retain answered questions and concise revision history when an answer changed. Reuse recorded answers instead of asking them again. Users may reply by question or request ID; clarify which question only when a request has multiple plausible unanswered questions.

Before finishing, reconcile the list against the conversation, host questions, decision records and unresolved facts. Convert any outstanding user-resolvable clarification, missing source or verification need into a question here; leave agent-owned investigation as an evidence limit. A default-only decision summary or a note saying “remains open” cannot replace the question, its options and answer status. Summaries may condense explanations, but must retain every question and its available options, recommendation and answer. Do not generate unnecessary questions merely to populate this section.
