# Change Report

Report what the selected change scope actually does in the application. Default to a short chat walkthrough. `detailed` adds source tables and relevant proof. Codex uses `$change-report`; Claude Code uses `/change-report`. These are agent-chat requests, not shell commands.

## Interface

Accept one scope: bare automatic, `latest`, `working`, `session`, or `--from A [--to B|working]`. `start` records a baseline before implementation. `detailed`, `--group role|page`, `--project ALIAS`, `--all`, `--plan "PATH" --phase ID`, `--verify`, `--save "PATH.md"`, and `help` can appear in any sensible order. `--all` selects all configured projects; it conflicts with `--project`. `--phase` requires `--plan`. `--save` writes only the requested Markdown file; refuse overwrite unless the user explicitly permits replacement. `--verify` runs focused relevant checks only when authorized by the target's rules, records exact outcomes, and never implies production proof. `help` returns short examples without inspecting or writing.

For multi-repository revisions, accept repeated `--repo-from NAME=REV` and `--repo-to NAME=REV` alongside a common `--from`/`--to`; the repository name must match the selected project member. A missing override uses the common revision and fails if it does not resolve. `--to` alone, competing scopes, unknown options, invalid revisions, and empty required arguments are errors. Do not silently substitute another scope.

Use [scripts/change_report.py](scripts/change_report.py) with Python 3.11+ and Git. Map chat scope to `inspect --scope auto|latest|working|session` or `inspect --from ... --to ...`; pass `--project`, `--all`, revision overrides, and a session token/context where relevant. The helper returns structured JSON evidence, not final prose. Read selected changed code, relevant routes, permission checks, navigation and requirements before writing. Never infer behavior, role access, or intent from filenames alone. Inspect tests and setup files as needed. Do not make application edits, stage, commit, switch branches, fetch, pull, push, or deploy.

## Scope and baselines

Bare scope order: matching current task baseline, otherwise uncommitted work, otherwise latest local commit. A baseline is current only when its token and task context match the active task; never choose an older stored run by timestamp. Explicit `session` without a matching baseline fails with a clear accuracy limit. `latest` compares HEAD to its first parent, or the empty tree for an initial commit; merge commits use first-parent comparison. `working` includes the current staged/unstaged tracked result plus relevant untracked files, excluding ignored, generated and sensitive paths. `--from A` targets HEAD; `--from A --to B` compares A directly with B, not their merge base; `--to working` uses the current worktree result. Identical snapshots yield a no-change report. A repository without commits supports `working` but not `latest`.

Before a task, run `start --context "<specific task/run identity>"` for every selected repository. Keep the returned token and exact context in the conversation or implementation handoff. During/after that task pass both to `inspect --scope session --token TOKEN --context CONTEXT`; use the same pair for bare auto selection. `start` stores pre-existing index and worktree line hashes, HEADs and repository roots under the invoking repository's Git metadata. It does not store source content or modify Git's index or worktree. If those two baselines differ, inspect marked ambiguous rows before attributing them to the task. If a sensitive or oversized dirty file is omitted, report incomplete scope; do not pretend its changes are attributable. Do not put secrets in the report or store unneeded files.

Project setup uses `project set --project ALIAS name=PATH ...` once, then `project list`. The helper stores the definition under the invoking repository's Git metadata, using nearby relative paths and explicit external paths. It resolves and deduplicates repository roots. Validate all selected members before reporting; missing members cause an explicit incomplete-selection error. Each member has independent revisions and baseline state. `--all` covers projects configured in this workspace only and reports unrelated projects in separate sections. Agent summaries support interpretation, but final integrated code and diff decide coverage. Changes in separate branches/worktrees are pending, not integrated.

## Write the walkthrough

Read [report format](references/report-format.md) for classification. Use the [brief](assets/brief.md) or [detailed](assets/detailed.md) template as a shape, never as evidence. Choose role or page grouping from inspected routes, permissions and navigation unless overridden. Group connected behavior across repositories into one walkthrough. Do not repeat a role on every line. Use actual page names, routes and button labels. Explain where to go, what to do, and what happens next. Include restrictions and required follow-up. Mention existing behavior only to clarify changed flow. No invented routes, promotional text, audience references, AI references, internal task IDs or unsupported claims.

Brief output omits hashes, branch metadata, file paths, line ranges, counts, type labels and routine verification. A short limitation note is allowed when scope or uncertainty otherwise misleads. Detailed output keeps the same walkthrough, then adds compact per-page/workflow source tables. Use relative paths and exact changed ranges: target lines for additions/modifications, baseline lines marked `old` for deletions, both paths for renames. Status (Added, Modified, Renamed, Deleted) and purpose (New, Improvement, Fix, Refactor, Removal, Unclear) are separate. A Fix needs expected-behavior evidence. Separate rows for distinct purposes in one file. Put a repository name above each table when several repositories contribute. Account for meaningful tests, migrations, configuration, dependencies and remaining files in compact supporting changes. Avoid generated diff dumps. Hashes only if explicitly requested.

Detailed verification distinguishes checks run now, existing records, code inspection, manual checks, Not run and Blocked. Test-file presence is not a pass. Add only concrete setup, incomplete work and evidence-based recommendations. An implementation-plan package uses `PLAN.md`, `CONTRACTS.md`, `PHASES.md`, `ACCEPTANCE.md`, `PROGRESS.md`, `HANDOFF.md` and the selected `prompts/Pxx_*.md` as available. These supply intended scope and recorded checks, not proof of completion. Reject a missing phase or package; compare selected acceptance against actual code and avoid claiming unrelated same-file changes belong to it. For end-of-phase integration, record `start` before implementation, complete the authorized phase and focused checks, then request `session --plan ... --phase ...`. Installation creates no automatic hook; add that explicit request to the execution prompt or existing supported integration.

## Generated artifacts

Normal reports stay in chat. Baseline hashes and project definitions live under the invoking repository's Git metadata in `change-report/` (or `CHANGE_REPORT_HOME` when deliberately set), outside tracked files and installed skill copies; runs use unique UTC `YYYYMMDDTHHMMSSZ-<id>` names and are never overwritten. `--save` writes the selected format to the explicit Markdown path only. For an in-repository generated report, check tracking and ignore rules first; do not hide user documentation or alter `.gitignore` merely to satisfy a save request. Refuse unsafe overwrite and explain the path. Preserve old baselines; resume with the recorded token/context.
